## 3. 過程中的失敗與修正（原始輸出摘要）
1. **fmt 檢查失敗**：第一次 `e2e-docker.sh` 在 `cargo fmt --check` 顯示多處 diff（新檔案未格式化）。以容器內 `cargo fmt` 修正。
2. **執行期找不到 SpanDSP 動態函式庫**：
   ```
   m0-...: error while loading shared libraries: libspandsp.so.4: cannot open shared object file
   ```
   根因：SpanDSP 在 Rocky 9 安裝到 `/usr/local/lib64`，但 Dockerfile 的 ld.so.conf 只列 `/usr/local/lib`（pkg-config 恰好能在 Rocky 預設路徑找到 lib64 的 .pc，所以編譯通過）。修正：Dockerfile 的 ld.so.conf 加入 `/usr/local/lib64`，`PKG_CONFIG_PATH` 也加入 lib64；重建映像。
3. **S09 初版高度不符**：
   ```
   assertion `left == right` failed: page 0 height  left: 1049  right: 1100
   ```
   根因見偏差 2。
4. **嘗試額外案例 S09b（ECM + 5% 遺失）失敗，已移除**：caller=21、answerer=36（皆非 0）。原因推測：本 loopback 模型的封包只有 `count` 份重複，沒有 UDPTL 的 secondary packet redundancy 或 FEC，因此在 ECM 下掉到關鍵控制封包就會使 T.30 序列失敗。這個案例不在計畫內，故移除而非調參；它也代表 S09 的通過仰賴 seed（見偏差 2 與未解事項）。

## 4. 與計畫的偏差
1. **FFI 與映像細節**：計畫指示的簽名皆經容器內標頭核對；`t30_set_*` 系列宣告在 `t30_api.h`。Dockerfile 依 ADR-007 從原始碼建置，TODO 中原寫的 `spandsp-devel（EPEL）`、`clang（bindgen）` 已改為此做法。
2. **S09 高度不要求完全相等**：計畫只要求「仍完成 1 頁」並斷言完成碼與頁數；本實作斷言完成碼 0/0、頁數 1、寬 1728，另斷言高度在來源的 90%–100%（990–1100）。實際收到 1049 列。理由：non-ECM 傳真遺失影像資料就遺失列，這是協定的正常行為，不是工具缺陷。這比「高度必須相等」弱，已明示。
3. **B02/B03/B04**：本機只能驗證 x86_64 musl 靜態連結與 `--version` 輸出；aarch64、Rocky/Alma 解壓執行、cargo-deny 依賴既有 CI job，本次未重跑。另新增 B03 的版本字串整合測試（計畫只有 B05）。
4. **loopback 延遲模型**：封包在產生的下一個 20 ms 步驟送達（單向延遲 20 ms），不模擬重排或抖動。
5. 未使用 `t38_set_t38_version`、`t38_terminal_set_tep_mode`（已宣告於 FFI，但 loopback 用預設值）。

## 5. 誠實性說明（給審核者）
- 每個 S04–S07、S09 測試都斷言兩端完成碼和收到頁數；S04–S07 另逐頁斷言寬高；S08 斷言 caller 非 0 且原因為 TIFF/F 無法開啟，並斷言未 timeout。
- 測試輸入由自寫 TIFF writer 產生，收到的檔案由獨立 reader 解析，只驗證中繼資料（頁數、寬、高），不比對像素內容（SpanDSP 輸出為壓縮格式，M0 沒有解碼器）。
- 沒有 mock SpanDSP；所有 S 案例都跑真實 SpanDSP v3.1.1。
- 未解事項：S09 目前只用一個固定 seed 驗證；其他 seed 或 ECM 下的遺失情境未驗證，應於 M2（加入 UDPTL redundancy）後補強。

## 6. Opus 審核結論（2026-10-20）
**結論：通過**，C01 視為有條件通過，待 GitHub 首次執行並列入必要檢查。

審核時重新執行了 `scripts/ci-local.sh`（含 Docker 內 SpanDSP 測試）。B05/B03 以及 S01–S10 全數通過，與報告一致。

審查重點：
- **斷言**：S04–S09 都斷言了雙方完成碼和頁數，沒有空斷言。
- **mock**：沒有 mock，測試直接打真實的 SpanDSP 3.1.1。
- **獨立驗證**：TIFF writer 和 reader 分屬不同模組，S03 另外用 libtiff 的 `tiffinfo` 交叉驗證。
- **記憶體安全**：callback 的 user_data 指向 `Box` 的穩定位址。Drop 的順序是先 free state，再釋放 box，正確。
- **路徑字串**：`CString` 傳給 `t30_set_tx_file`/`t30_set_rx_file` 後就被釋放。查證 SpanDSP 3.x 會把路徑複製到內部 buffer，所以沒有懸空指標。
- **S09 高度改用範圍斷言**：non-ECM 遺失影像資料本來就會少掉列，是協定的正常行為，接受。
- **審核時修正**：`scripts/e2e-docker.sh` 原本在映像已存在時就不重建，會導致修改 Dockerfile 後仍沿用舊映像。已改為每次都 `docker build`（有 layer cache，速度影響不大）。
