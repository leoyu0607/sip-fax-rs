`tests/rfc4475.rs` 的 `cases()` 表是權威版本，下表為摘要。「拒絕」＝`parse_message`／`parse_datagram` 回對應的 `ParseError`；「容忍」＝解析成功，由上層回應。

| badinv01 | 3.1.2.1 | 拒絕 `InvalidHeader`（Via 空元素）| 語法無效，400 |

## 4. 遇到的失敗與根本原因（原始輸出摘錄）

1. **真實 bug：起始行解析在非 UTF-8 邊界切片會 panic**（proptest 找到）
   ```
   thread 'p10_mutated_valid_messages_never_panic_and_survivors_reserialise' panicked at crates/sip-core/src/message/parse.rs:326:31:
   byte index 4 is not a char boundary; it is inside '�' (bytes 2..5) of `!i�teresting-Method0123456789_*+`.%indeed'~ sip:... SIP/2.0`
   minimal failing input: which = 2, edits = [(Index(57556143755724031), 128)], cut = None
   ```
   （`p10_arbitrary_bytes_never_panic` 同樣失敗。）根因：`line[..4].eq_ignore_ascii_case("SIP/")` 對 `&str` 以 byte 索引切片，遇到多位元組字元會 panic。修正為對 `line.as_bytes()[..4]` 比對。迴歸案例保存於 `tests/message.proptest-regressions`。這正是「有 proptest」的價值：RFC 向量與手寫案例都沒有踩到。
2. **fuzz 找到的不是 parser bug，而是我 fuzz 目標的不變量寫錯**（`parse_sdp`，60 秒內）
   ```
   assertion `left == right` failed: serialise/parse is not a fixed point
   ```

## 7. 與計畫／規格的偏離（含理由）

1. **`parse_message(&[u8])` 簽名**：規格為單一函式。實作為 `parse_message(buf)`（串流模式，回傳 `(SipMessage, consumed)`，與規格一致）加 `parse_datagram(buf) -> Result<SipMessage>` 與通用 `parse_with_framing(buf, Framing)`，因為 P06/P07 需要兩種模式。
2. **新增 `Uri` enum（ADR-009）**：規格寫 `SipUri` 對 sip/sips/tel 以外「拒絕」，但 RFC 4475 3.3.2/3.3.3/3.3.4 要求 parser 接受其他 scheme。`SipUri::parse` 仍拒絕；`Request::uri` 和 `NameAddr::uri` 型別為 `Uri`（`Sip(SipUri)` ｜ `Other{scheme,rest}`）。
3. **inv2543 被拒絕**：規格第 2 節要求缺 Max-Forwards 回 `ParseError`，與 RFC 4475 3.4.1 的向後相容建議衝突；依規格拒絕並在測試中標明。
4. **header 值若含非 UTF-8 位元組會以 U+FFFD 取代**（起始行與 header；body 一律保持原始 bytes）。規格寫「保留未知 header 的原文」；對有效 UTF-8（RFC 4475 所有向量皆是）完全保留。取捨：用 `String` 簡化 API；若 M6 的真實 trace 顯示需要保留 Latin-1 之類，再改為 bytes。
5. **未知 header 名稱保留原拼法，已知名稱正規化為標準大小寫**（規格只說「保留原文」）；序列化沿用解析時的縮寫／全名選擇。
6. **`Content-Length` 留在 `Headers` 內**，序列化時就地重算並保留原拼法（縮寫 `l` 也保留），重複的刪除；因此 round-trip 測試以「補上 Content-Length 後相等」為預期。
7. **SDP**：`Origin.sess_id` 是 `u64`（超過的 id 會被拒絕）；`s=` 缺少時容忍（`session_name: None`）；未知行序列化時移到 RFC 4566 規定的位置（見第 4 節第 2 項）；T.38 缺少的選用屬性預設值為 version 0、MaxBitRate 14400、transferredTCF、MaxBuffer 1800、MaxDatagram 260、UdpEC Redundancy——規格只指定了 version 0 與「UdpEC 依對方」，其餘是我選的（`sdp::t38::defaults`），**需要 Opus 確認**。T.38 布林屬性輸出：true 寫成裸名稱，false 省略。
8. **mpart01 等向量由 RFC 附錄 A 的 bit-exact 壓縮檔直接解出**（不是手抄），因此沒有轉錄誤差；`<hex>`、`<repeat>`、`<allOneLine>` 標記不需要處理。README 在 `tests/vectors/rfc4475/README.md`。
9. **Digest**：新增 `from_header_value` 與 `build_authorization_with_cnonce`（決定性測試用）；詳見 `docs/sipress-extraction.md`。
10. **依賴**：新增 md-5（ADR-008）。`tokio`、`tracing` 宣告在 workspace 但 M1a 的 sip-core 尚未使用（避免未使用依賴）。
11. **sdp 向量為手寫**：`tests/vectors/sdp/README.md` 已註明是代表性樣本、非實機擷取。
12. lib 層級加上 `deny(missing_docs)` 與（非測試程式碼）`deny(clippy::unwrap_used, expect_used, panic, unreachable)`，編譯器強制「公開項目有 rustdoc」與「不對不受信任輸入 unwrap」。陣列／切片索引的安全則靠 proptest 與 fuzz 驗證（第 4 節第 1 項證明這個驗證是有效的）。

## M1b-4. 過程中失敗的項目、原始輸出與根因
1. `t03_timer_g_intervals_are_capped_at_t2_and_scale_with_t1` 首次執行失敗：
   ```
   panicked at crates/sip-core/tests/transaction.rs:334:26:
   range end index 6 out of range for slice of length 5
   ```
   根因：測試錯誤。T1=100 ms、T2=700 ms 時重送時間點為 0, 100, 300, 700, 1400, 2100, 2800；我只觀察到 2500 ms，只拿到 5 個間隔卻要比對 6 個。改為觀察到 3000 ms（實作行為正確）。
2. `c04_registrar_timeout_fails_after_timer_f_then_retries_and_recovers` 首次執行失敗：
   ```
   assertion `left == right` failed: Timer E retransmissions
     left: [0, 500, 1500, 3500, 7500, 11500, 15500, 19500, 23500, 27500, 31500]
    right: [0, 500, 1500, 3500, 7500, 15500, 31500]
   ```
   根因：測試錯誤。我把 INVITE 的 Timer A（不受 T2 限制）的序列套在 non-INVITE 的 Timer E（上限 T2=4 s）上。REGISTER 是 non-INVITE，實作行為（與 T10 一致）正確，已更正預期。
3. `n02_udp_garbage_and_oversize_datagrams_are_dropped_and_the_loop_survives` 首次執行失敗：
   ```
   called `Result::unwrap()` on an `Err` value: Os { code: 40, kind: Uncategorized, message: "Message too long" }
   ```
   根因：測試環境限制。macOS 的 UDP 資料報上限為 9216 bytes（`net.inet.udp.maxdgram`），66,000 bytes 的測試資料報無法送出。改為 8000 bytes，並將函式更名為 `..._large_datagrams_...`；**64 KiB 上限本身由 P09 驗證**，不由此測試負責。
4. `c01_reject_mode_answers_403_and_delivers_nothing` 首次執行失敗：
   ```
   left:  "SIP/2.0/UDP 127.0.0.1:65409;rport=65409;branch=z9hG4bKc01rej;received=127.0.0.1"
   right: "SIP/2.0/UDP 127.0.0.1:65409;rport=65409;branch=z9hG4bKc01rej"
   ```
   根因：測試預期有誤。Via 帶 `rport` 時規格要求同時補 `received`（第 3 節），403 的 Via 因此正確地含有 received。已修正預期。
5. `StreamDecoder` 單元測試 `n04_byte_by_byte` 失敗（`left: ["OPTIONS", "200"]  right: ["OPTIONS", "PING", "200"]`）：**真實的實作 bug**。逐 byte 餵入時，keep-alive 的第一個 `\r` 單獨到達，`take_frame` 會把它當成訊息間的空白吃掉，ping 因此遺失。修正：buffer 恰為 `\r` 時等待下一個 byte。修正後 `n04_every_split_point...` 與逐 byte 測試皆通過。
6. clippy：`identity_op`（`t3 - 0 - ...`）、`redundant_pattern_matching`，皆為測試程式碼，已修正。

## M1b-6. 與計畫／規格的偏離與取捨（含理由）
1. **T03 數字的解讀**：計畫寫「Timer G 在 500、1000、2000、4000、4000…ms 重送」，我把它解讀為**間隔**（與 RFC 3261 及 G02「0、500、1500、3500、7500、11500」一致），累計時間點為 500、1500、3500、7500、11500…；報告同時列出兩者。T07 的「500、1500、3500」則是累計時間點。
2. **ICT 收到重送的 2xx 一律吸收**（計畫 T09 要求）。RFC 6026 本身是把每個 2xx 都交給 TU 以便重送 ACK；因此 M1c 的 Dialog 層需要另行處理「2xx 重送時的 re-ACK」（例如新增「重複 2xx」事件）。記錄於 ADR-010，列為待辦。
3. **Max-Forwards**：依 Opus 審核修正為選用（ADR-010）。
4. **來源政策只套用在 request**；response 不過濾（C01 `c01_responses_are_not_filtered`），因為回應來自我們自己選的對象。`Drop` 模式在 TCP 上會關閉連線；`Reject` 模式對 ACK 不回應（ACK 沒有回應）。
5. **入站 Via 的 `received` 一律先移除再決定是否補上**（RFC 沒有明講；頂端 Via 是上一跳寫的，不能讓對方用偽造的 `received` 操控我們的回應路由，`n02_spoofed_received_is_discarded`）。
6. **無法解析的入站資料不回 400**：規格寫「可以回應的情況回 400」，M1b 的 transport 只記 debug log 並丟棄（UDP 資料報、TCP 的 `Malformed`）。是否回 400 需要 UAS 層判斷（要有可解析的 Via/To/From），留給 M1c 的 endpoint；TCP 框架失效（`Fatal`）則關閉連線。
7. **TCP 連線池只在設定 `tcp_bind`（有 listener）時存在**；不支援「只有主動連線、沒有 listener」的配置。M1b 範圍的用法（trunk 皆有固定 IP）不需要；若 M1c 需要再調整。
8. **Timer D 預設固定 32 s（可設定）、Timer M 在 TCP 也是 64·T1**。RFC 3261 對 UDP 要求 D ≥ 32 s；RFC 6026 的 Timer M 不分傳輸。
9. **「不可真的 sleep」的範圍**：T01–T13、C03、C04 全部使用 `start_paused = true`，沒有任何真實 sleep。N 與 C01 使用真實 socket；負向斷言（「沒有送出任何東西」）等待真實 300 ms，閒置逾時測試使用真實 300 ms 的逾時設定（paused time 搭配真實 socket 會讓 runtime 在等待 I/O 時自動快轉，不可靠）。這些不屬於計時器精確度測試。
10. **Registration**：未處理 423 Interval Too Brief／Min-Expires 與 Retry-After；只對 `Expires`／Contact 的 `expires` 參數取得授予時間；只支援 MD5 digest（auth.rs 的限制）。
11. **TuEvent／API 命名**：`TuInput::{Request, Ack, StrayResponse, Stateless}` 與 `TuEvent::{Response, Ack, Cancelled, Timeout, TransportError}` 為我新設計的（規格只有模組結構）。TransportError 事件規格沒有提到；RFC 要求 transport 失敗時通知 TU 並終止。
12. `Response::for_request`、`Headers::set_first`、`Via::remove_param`、`StatusCode::FORBIDDEN` 為本階段新增的小 API。
13. **CI 兩個 job 都沒有在 GitHub 上實際跑過**（本環境不 push）；本機以同一指令驗證（coverage 指令、fuzz 目標各 45 秒）。

## M1b — Opus 審核結論（2026-10-20）
**結論：通過**，附帶下列項目，全部列為 M1c 必做。

已檢查：
- 計時器全部以 paused time 斷言到精確的毫秒。
- C03 的 digest 用外部 `md5` 獨立重算，不依賴受測程式碼。
- 來源政策的三種模式都用真實 socket 驗證。
- 失敗紀錄都附上原始輸出和根因。
- 真實 bug（StreamDecoder）已修正，回歸測試也保留下來。

**必修（重要）：**
1. **2xx 重送時必須重送 ACK。** 我方發出 re-INVITE、收到 200 之後，若我方的 ACK 遺失，對方會重送 200。目前 ICT 在 Accepted 狀態會吸收重送的 200，dialog 層因此永遠不會重送 ACK。結果是對方等不到 ACK，大約 32 秒後掛斷，而傳真正是在切到 T.38 之後才開始傳送。
   - 根因是測試計畫 T09 寫得不完整（Opus 的責任）。
   - 修正方式：ICT 在 Accepted 狀態把重送的 2xx 以 `TuEvent::Retransmitted2xx` 交給上層，由 dialog/UAC core 重送暫存的 ACK。
   - 新增案例 **G16**：在 paused time 下丟掉第一個 ACK，收到重送的 200 時，同一個 ACK 的 bytes 要重送；SIPp 版本 **S11**：SIPp 對我方 re-INVITE 回 200，並在收到 ACK 前重送兩次 200。
   - T09 的斷言同步修正。
2. **re-INVITE 的應用層逾時。** ICT 進入 Proceeding 後就取消 Timer B，這符合 RFC。但如果對方只回 100、一直不送最終回應，`reinvite()` 就會永遠卡住。dialog 層要有可設定的逾時（預設 32 秒），逾時後送 CANCEL，並回傳 `ReinviteOutcome::Timeout`。新增案例 **G17**。
3. **註冊要處理 423 和 Retry-After。** 收到 423 時，依 Min-Expires 調高 Expires 後立即重送；收到 503 或 Retry-After 時，依它指定的秒數再重試。新增案例 **C04b**。CS210 沒有規格文件，無法排除這些情況。
4. **無法解析的 request 回 400。** 只要能取得 Via、From、To、Call-ID、CSeq，就回 400；取不到就丟棄。在 endpoint 層實作，新增案例 **E06**。

其他確認：`transaction/machine.rs` 的涵蓋率 68%，未涵蓋的是被覆寫的 trait 預設方法，可以接受。
