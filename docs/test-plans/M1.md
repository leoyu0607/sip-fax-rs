# M1 測試計畫：sip-core

- 撰寫：Opus
- 執行：Sonnet
- 審核：Opus
- 規格：`docs/design/sip-core.md`
- 獨立驗證來源：自寫的 UAC（fax-sim）只能證明我們自己跟自己相容。所以 M1 引入 **SIPp 3.8.0**（第三方實作）當作主要的對手端，並用 RFC 4475 測試向量檢驗 parser。

## 0. 共通規則
- 測試函式以案例 ID 開頭，例如 `p03_folding_unfolded`。
- 計時器測試一律使用 `tokio::time::pause()`，時間點要斷言到毫秒且必須精確相等。禁止使用真實的 sleep。
- 每個案例都要斷言**實際送出的線上 bytes** 或**解析後的欄位值**。不能只斷言 `is_ok()`。
- **涵蓋率門檻**：`sip-core` 的 line coverage 至少 85%，以 `cargo llvm-cov` 量測。CI 加入 `coverage` job 來強制這個門檻。

## 1. Parser 與訊息（P）
| ID | 案例 | 預期 |
|---|---|---|
| P01 | RFC 4475 3.1.1 所有 valid 訊息（wsinv、intmeth、esc01、escnull、esc02、lwsdisp、longreq、dblreq、semiuri、transports、mpart01、unreason、noreason）| 全部解析成功，並抽查關鍵欄位（例如 wsinv 的 Call-ID、longreq 的 header 數量）|
| P02 | RFC 4475 3.1.2 所有 invalid 訊息（badinv01、clerr、scalar02、scalarlg、quotbal、ltgtruri、lwsruri、lwsstart、trws、escruri、baddate、regbadct、badaspec、baddn、badvers、mismatch01、mismatch02、bigcode、badbranch 等）| 依 RFC 的說明，應拒絕的回 `ParseError`，可容忍的則解析成功。每一個向量都必須寫出期望結果並附上理由 |
| P03 | header folding | 展開後的值正確 |
| P04 | compact form 全部 16 種 | 正規化成完整名稱，序列化時保留原本使用的形式 |
| P05 | 多值 header 拆分 | 引號字串和 `<>` 內的逗號不拆；多個 Via 的順序保持不變 |
| P06 | Content-Length（串流模式）| 缺少時回錯誤；兩則訊息黏在同一個 buffer 時，回傳的已消耗長度正確；body 只到一半時回 `Incomplete` |
| P07 | Content-Length（資料報模式）| 缺少時以剩餘位元組為 body；過大回錯誤；過小則截斷 |
| P08 | 必要 header 缺少 | 每一種缺少都回 `ParseError::MissingHeader(name)` |
| P09 | 大小上限 | 超過 64 KiB 或超過 256 個 header 時拒絕 |
| P10 | round-trip 屬性測試（proptest）| 隨機產生 Request/Response，序列化後再解析，結果相等；任意 bytes 輸入不會 panic |
| P11 | sipress 抽取的 `take_frame` 測試 | 原本的測試搬過來後全部通過 |
| P12 | cargo-fuzz 目標 `parse_message` 和 `parse_sdp` | 建立 fuzz 目標；CI nightly 排程跑 5 分鐘不 crash（M1 先建立目標，本機跑 60 秒）|

## 2. SDP（D）
| ID | 案例 | 預期 |
|---|---|---|
| D01 | 解析並序列化 Sonus 和 AudioCodes 風格的 audio offer，以及 T.38 re-INVITE offer（範例放在 `tests/vectors/sdp/`，依廠商公開文件格式撰寫）| 欄位正確，round-trip 完全相同 |
| D02 | T.38 屬性變體：大小寫、布林兩種寫法、缺少選用屬性 | 解析成功；缺少的屬性套用規格預設值（Version 0、UdpEC 依對方…）|
| D03 | T.38 answer 協商矩陣：version 0–3 × MaxBitRate（2400–33600）× RateManagement × UdpEC（FEC、Redundancy、NoEC）| 每一格都符合規格第 6 節的規則（table-driven）|
| D04 | audio answer：PCMU/PCMA 交集、telephone-event 保留、無交集 | 交集時選出正確的 payload；無交集時回 `NoCommonCodec` |
| D05 | 拒絕 m-line | 該 m-line 的 port 為 0，其餘欄位保留 |
| D06 | o= 版本規則 | 內容改變時版本加一，內容相同時版本不變 |
| D07 | proptest：任意 bytes 輸入 | SDP 解析不會 panic |

## 3. Transport（N）
| ID | 案例 | 預期 |
|---|---|---|
| N01 | UDP 收到 request，Via 帶 rport | 補上 `received` 和 `rport=<port>`，回應送到來源 IP 和來源 port |
| N02 | UDP 收到 request，Via 沒有 rport，sent-by 與來源不同 | 補上 `received`，回應送到 received 加 sent-by port |
| N03 | TCP 收到 request | 回應走原本的連線；連線斷掉時依 sent-by 重新連線 |
| N04 | TCP 黏包和拆包（同一個 segment 有兩則訊息、一則訊息拆成三個 segment）| 兩則都正確交付 |
| N05 | keep-alive | 收到雙 CRLF 時回單 CRLF；收到單 CRLF 時忽略 |
| N06 | 送出 request | 頂端 Via 的 transport 和 sent-by 使用設定的對外位址 |
| N07 | IPv6 | 綁定 `[::1]`，以 UDP 收發成功，Via 的 sent-by 格式正確 |

## 4. Transaction（T）（全部使用 paused time）
| ID | 案例 | 預期 |
|---|---|---|
| T01 | INVITE server：TU 200ms 內沒有回應 | 在 200ms 時送出 100 |
| T02 | INVITE server：收到重送的 INVITE | 重送最後一個 provisional；送出 2xx 之後（Accepted）收到則吸收，不交給 TU |
| T03 | INVITE server：最終回應 486 | Timer G 在 500、1000、2000、4000、4000…ms 重送；收到 ACK 後停止；Timer I 結束後終止 |
| T04 | INVITE server：486 沒有收到 ACK | Timer H 在 32s 時通知 TU，期間的重送次數正確 |
| T05 | INVITE server：RFC 6026 Accepted | ACK 交給 TU；Timer L 到期後終止 |
| T06 | non-INVITE server | 收到重送時重送最終回應；UDP 的 Timer J 為 32s，TCP 為 0 |
| T07 | INVITE client（UDP）| Timer A 在 500、1500、3500…ms 重送；Timer B 在 32s 時逾時並通知 TU |
| T08 | INVITE client 收到 4xx | 自動送出 ACK，且 ACK 的 branch、Via、To tag 正確；收到重送的 4xx 時重送 ACK；Timer D 結束後終止 |
| T09 | INVITE client 收到 2xx | 交給 TU；收到重送的 2xx 時不再重複上報 TU |
| T10 | non-INVITE client | Timer E 的重送間隔正確（收到 provisional 之後改用 T2）；Timer F 逾時；Timer K |
| T11 | TCP 上的 INVITE client 和 server | 不重送 |
| T12 | CANCEL | 對還沒送出最終回應的 INVITE 發 CANCEL：CANCEL 收到 200，INVITE 收到 487；沒有對應交易時 CANCEL 收到 481 |
| T13 | 交易比對 | 相同 branch 但 method 不同、相同 branch 但 sent-by 不同，都算不同交易；ACK 對應到非 2xx 的 INVITE 交易 |

## 5. Dialog 與 UAS core（G）
| ID | 案例 | 預期 |
|---|---|---|
| G01 | 從 INVITE 建立 dialog：帶兩個 Record-Route | route set 順序正確；remote target 為 Contact |
| G02 | 2xx 重送 | 沒有收到 ACK 時，在 0、500、1500、3500、7500、11500…ms 重送 200；收到 ACK 就停止 |
| G03 | ACK 逾時 | 64·T1 到期時上報 `AckTimeout` |
| G04 | 我方 BYE（loose routing）| Request-URI 為 remote target，Route 為 route set，CSeq 加一，tag 正確，送往第一個 route |
| G05 | 我方 BYE（strict routing）| Request-URI 為第一個 route，remote target 放在 Route 的最後 |
| G06 | 對方 BYE | 回 200；dialog 結束；之後收到的 in-dialog request 回 481 |
| G07 | 對方 re-INVITE（帶 T.38 offer）| 上層收到 offer；回 200 加 answer；收到 ACK |
| G08 | glare：我方 re-INVITE 還在進行時收到對方 re-INVITE | 回 491 |
| G09 | 我方 re-INVITE 收到 491 | 在 0–2s 內重試（paused time 下檢查重試時間落在區間內）；超過上限時回報 Rejected(491) |
| G10 | CSeq 比 remote seq 小 | 回 500 |
| G11 | OPTIONS（dialog 內和 dialog 外）| 回 200，並帶 Allow、Accept、Supported |

## 7. 第三方互通：SIPp（S）（在 Rocky 9 容器中執行）
- Scenario XML 放在 `tools/sipp/`，對手端是一個以 sip-core 寫成的最小 UAS 測試程式（`tools/fax-sim` 的 `uas-test` bin），它的行為可以設定。
- 每個 scenario 都要檢查 SIPp 的 exit code 為 0，並且斷言 SIPp 統計中的 `Successful call` 數量。

| ID | 案例 | 預期 |
|---|---|---|
| S01 | 基本來電（模擬 gateway）：INVITE（G.711）→ 100/180/200 → ACK → 我方 re-INVITE(T.38) → SIPp 回 200 → ACK → SIPp 送 BYE | 成功 |
| S02 | gateway 發起：SIPp 在 ACK 後送 T.38 re-INVITE，我方回 200 加 T.38 answer（SIPp 驗證 `m=image` 和屬性）| 成功 |
| S03 | SIPp 不回 ACK | 我方以 G02 的時間點重送 200（SIPp 以 `recv` 計次），最後 SIPp 收到 BYE |
| S04 | SIPp 重送 INVITE（模擬遺失 100）| 我方重送回應，不會建立第二個 dialog |
| S05 | Record-Route（SIPp 模擬兩個 SBC 加入 Record-Route）| 我方的 BYE 和 re-INVITE 帶有正確的 Route 和 Request-URI（SIPp 以 regex 驗證）|
| S06 | 我方 re-INVITE 收到 SIPp 回的 491 | 我方在 2s 內重試，第二次成功 |
| S07 | SIPp 對 T.38 re-INVITE 回 488 | 我方送 ACK；dialog 仍然存在；SIPp 送 BYE 時收到 200 |
| S08 | CANCEL：SIPp 在 180 之後送 CANCEL | 我方對 CANCEL 回 200、對 INVITE 回 487，SIPp 送 ACK |
| S09 | TCP 傳輸重跑 S01 | 成功 |
| S10 | 負載：SIPp 以 20 cps 打 200 通 S01 的簡化流程 | 成功率 100% |
